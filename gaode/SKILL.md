# 高德周边去哪儿

## 用途与适用场景

将用户的城市、起点和自然语言偏好转换为一次可核验的附近地点推荐。评测环境会提供起点坐标和高德 MCP 工具；优先使用工具返回的真实地点和步行路线，不依赖常识、记忆或虚构数据。本 Skill 适用于从同一个起点选择附近地点，不用于规划多站行程。

## 执行流程

1. **理解需求。** 提取并保留以下约束：城市、起点（优先使用评测提供的坐标）、地点类型和关键词、步行时间上限、推荐数量上限，以及排序偏好（例如“优先近一点”）。地点类型不明确时，先根据用户原话确定搜索词；不要擅自替换成无关类别。未指定数量时最多推荐 3 个。

2. **搜索地点。** 调用高德 MCP Server 的地点搜索能力（若运行环境中的工具名称不同，选择工具描述明确对应“地点搜索”的那个），以起点坐标为中心并带上城市限制和地点类型/关键词，获取一组候选。搜索结果中的名称、地址、坐标和 POI 标识是候选的唯一事实来源。需要更多候选时可以扩大搜索范围或补充同义关键词，但必须仍然符合用户的地点类型，并在回答中说明范围已扩大。不要凭记忆添加搜索结果之外的地点。

3. **逐个查询步行路线。** 对每个有希望入选的候选地点，分别调用高德 MCP Server 的步行路线规划能力（选择工具描述明确对应“步行路线”的那个），起点始终是用户给出的同一起点，终点使用该候选的高德坐标或 POI 标识。各候选是独立备选，不要把它们串成一条多站路线。以路线工具返回的步行距离和预计时长为准，绝不能用直线距离、地图目测或固定速度估算替代。若返回多条步行方案，采用工具标示的推荐方案，并保留其距离和时长。

4. **筛选与排序。** 先按用户的硬性条件筛选，再排序和截取数量：
   - 有步行时间上限时，只把路线原始时长不超过上限的地点列为符合条件的推荐；边界判断使用工具返回的原始数值，不能因四舍五入把超时地点列入。
   - 没有可用步行路线的地点不能写成“可步行到达”，应从符合条件的推荐中排除，必要时单独说明路线查询失败。
   - 用户说“优先近一点”时，按步行距离升序；距离相同再按步行时长升序。其他排序要求也必须以路线数据和搜索相关性为依据。未指定排序时，优先相关性，再按步行时长升序。
   - 最多返回用户要求的数量，默认最多 3 个。数量不足时少推荐，不要用未查询或不符合条件的地点凑数。

5. **生成回答。** 使用中文、简洁列表或表格回答。每个推荐必须包含：
   - 地点名称
   - 高德搜索结果中的地址
   - 从起点出发的预计步行距离
   - 从起点出发的预计步行时间
   - 一句只基于已查询事实的推荐理由（例如“在时间上限内且步行用时最短”或“与用户指定类型匹配”）

   距离和时长可以将工具单位转换为米/公里和分钟，但不得改变原始含义；时间上限判断仍使用原始时长。推荐前可用一句话交代筛选口径，例如“以下均为从该起点独立步行可达的地点”。

## 异常与信息边界

- 地点搜索为空时，如实说明当前城市、搜索范围和地点类型下没有找到结果；可以建议用户放宽范围、类型或步行时间，不要编造替代地点。
- 搜索结果少于用户要求数量时，返回实际符合条件的结果，并明确说明“仅找到 N 个符合条件的地点”。
- 步行路线服务暂时失败时，可对同一候选重试一次；仍失败则说明无法核实路线，并不输出猜测的距离或时间。若服务整体不可用，应简短说明查询失败。
- 营业状态、排队情况、安静程度、价格、评分、是否有座位等信息，只有在本次工具结果明确提供时才能陈述；否则标注“未核实”，或不要提及。不要把搜索排序、名称或常识当作这些属性的证据。
- 不展示、索要或生成高德 API Key。工具调用记录由平台采集，无需输出 JSON、日志或内部调用细节。

## 推荐回答模板

```text
根据你提供的起点，按步行路线查询结果，推荐以下地点（最多 N 个）：

| 地点 | 地址 | 步行距离 | 预计时间 | 推荐理由 |
| --- | --- | ---: | ---: | --- |
| 地点名称 | 高德返回的地址 | 工具返回的距离 | 工具返回的时长 | 与需求和路线数据对应的理由 |

补充说明：若结果不足、路线失败或某些属性未核实，在这里用一句话说明。
```

只把经过地点搜索和步行路线查询、且满足硬性条件的地点放入表格。若没有符合条件的地点，直接说明结果为空及可放宽的条件，不要输出示例地点或虚构路线。
